# BornCode — บอร์ดงานซ่อม (ตัวอย่าง)

> **ตัวอย่างนี้เขียนขึ้นใหม่ทั้งหมด** เพื่อแสดงแนวคิดการออกแบบของระบบจัดการงานซ่อมแบบไม่ใช้กระดาษ
> ข้อมูลทุกรายการเป็นข้อมูลสมมติ ไม่มีข้อมูลจากองค์กรใด — ดูรายละเอียดเรื่องที่มาใน
> [ที่มาและขอบเขต](#ที่มาและขอบเขต)

ไฟล์เดียว เปิดด้วยเบราว์เซอร์ได้เลย ไม่ต้องติดตั้ง ไม่ต้อง build ไม่ต้องมีเซิร์ฟเวอร์
ไม่มี dependency และไม่ต่อเน็ตใด ๆ ระหว่างใช้งาน

```
open index.html          # macOS
start index.html         # Windows
xdg-open index.html      # Linux
```

หรือเปิดในเบราว์เซอร์แล้วกดลากไฟล์เข้าไป ถ้าอยากให้เป็นเว็บจริง: `python -m http.server` แล้วเปิด
`http://localhost:8000`

## ในตัวอย่างนี้มีอะไร

| | |
|---|---|
| **แจ้งเรื่อง** | ฟอร์มสั้น ๆ ไม่ต้องมีบัญชี — เลือกสาขา ประเภทงาน กรอกรายละเอียด แล้วส่ง ขึ้นกระดานทันที |
| **กระดานงาน** | การ์ดงาน ตัวกรองตามสถานะ/ประเภท ค้นหา มอบหมายช่าง ปิดงานพร้อมให้คะแนน และเปิดงานที่ปิดแล้วกลับมาได้ |
| **บันทึกการเปลี่ยนแปลง** | ทุกการแก้ไขเก็บว่าใคร เปลี่ยนอะไร จากอะไร เป็นอะไร เมื่อไร — เปิดดูย้อนหลังได้ |
| **ภาพรวม** | งานค้าง งานที่เสร็จ คะแนนเฉลี่ย โหลดงานต่อช่าง และกราฟงานรายประเภท |

กติกาที่ฝังอยู่ในตัวอย่าง: คะแนน 1–2 ต้องเขียนเหตุผลเสมอ (คะแนนต่ำต้องมีคำอธิบายติดมา)
และการปิดงานต้องมีสรุปสิ่งที่ทำ — คือกัน "ปิดงานแล้วเงียบ ๆ" ซึ่งเป็นสาเหตุที่ผลตอบรับหาย

## ระบบจริงที่ผมพัฒลา

ผมพัฒนาระบบจัดการงานซ่อมนี้ระหว่างที่งาน สำหรับทีมงานที่ดูแลอาคารหลายสิบสาขา
ระบบตัวนี้ถูกใช้งานจริงและปล่อยรุ่นต่อเนื่องหลายเดือน ผมเล่าให้ฟังในฐานะผู้ทำ เพราะ
เป็นงานที่สอนอะไรผมมากที่สุดในชีวิตการทำงาน

### ปัญหาที่ต้องแก้

ทีมงานแจ้งงานผ่านกระดาษ ผลคือข้อมูลหาย ไม่รู้ว่าใครรับงานอะไรไว้ นับงานค้างไม่ได้
และผลตอบรับกลับมาไม่ครบ ระบบใหม่ต้องทำให้ "คนที่อยู่หน้างาน" แจ้งงานได้ใน 20 วินาที
โดยไม่ต้องมีบัญชี แล้วให้ "คนที่ดูแล" เห็นภาพรวมทั้งหมดในหน้าจอเดียว

### สองทางเข้า

1. จุดใช้งานแต่ละสาขามีการ์ดพร้อม QR → สแกนแล้วเจอฟอร์มบนมือถือ → ส่งเรื่อง
2. ฝั่งดูแลระบบ: triage → เลือกแผนก → มอบหมายช่าง → ติดตาม → ปิดงาน → เก็บคะแนน

### สแต็ก

Next.js 14 (App Router) · TypeScript · React 18 · Tailwind v4 · Prisma 5 · PostgreSQL 16 ·
iron-session (cookie auth) · bcrypt · Nodemailer · Chart.js · Docker Compose +
Cloudflare Tunnel (self-hosted) และ Vercel serverless เป็นอีกเส้นทาง deploy ·
Jest + Supertest กับชุดทดสอบ 584 เคส · k6 สำหรับ load test เส้นทางแจ้งเรื่อง

### สิ่งที่ยากกว่าที่คิด — ส่วนที่ผมภูมิใจที่สุด

1. **เดือนไม่ตรงเพราะเวลา** ฐานข้อมูลเก็บ UTC แต่รายงานรายเดือนต้องนับตามเวลาไทย
   ขอบเดือนจึงเลื่อนไป 7 ชั่วโมง งานที่ปิดตี้หนึ่งคืนหนึ่งทุ่มต้องอยู่เดือนก่อนหน้า
   แก้ที่ระดับ helper เดียวแล้วให้ทั้งหน้าจอกับไฟล์ export ใช้กติกาเดียวกัน
2. **ฟอร์มสาธารณะคือข้อมูลที่ไม่เชื่อถือ** ทั้งฟอร์มรับเรื่องและไฟล์ Excel ที่ export ออกไป
   ต้องกันฟอร์มูลฟอร์มัล (ข้อความที่ขึ้นต้นด้วย `=` ใน Excel), XSS, และการยิง login เพื่อเดา
   รหัสผ่าน — จุดเหล่านี้เป็นเหตุผลที่สาธารณะมากกว่าภายในต้องคิดเรื่องความปลอดภัยเข้มกว่าปกติ
3. **Authorization ต้องมีนโยบายเดียว** ตอนแรกสิทธิ์ถูกเช็คหน้าจอ พอมาเจอ endpoint ที่รั่ว
   ก็ต้องรื้อมาเขียนใหม่ทั้งชั้น API — ปิดท้ายด้วยกฎเดียวที่ทั้ง API และ UI ใช้ร่วมกัน
4. **ข้อมูลส่วนบุคคลต้องถูกซ่อนตามบทบาท ไม่ใช่ซ่อนทั้งระบบ** เบอร์โทรของช่างจำเป็น
   กับคนดูแล แต่ไม่จำเป็นกับทุกบทบาท — แก้ทั้ง API และ payload ที่ซ้อนอยู่ในใบงาน
5. **Migration บน production ต้องแยกจาก build** build สองตัวที่รันพร้อมกันจะแย่ง lock กัน
   เลยต้องแยกขั้นตอน "apply schema" ออกจากขั้นตอน "build"
6. **Backup ที่ไม่เคยกู้คืนจริง คือไม่ใช่ backup** — เขียนเป็น ADR (Architecture Decision Record)
   ตัดสินใจเป็นลายลักษณ์อักษร พร้อมระบุว่าจะกู้คืนยังไง ไม่ใช่แค่ก๊อปไฟล์ไว้
7. **ลิงก์ในอีเมลต้องชี้กลับมาที่ตัวเอง** ระบบที่ deploy หลายที่ต้องมีตัวแปร `APP_URL`
   เดียวคุมทั้งลิงก์ในเมลและการ์ด QR ที่พิมพ์ออกไป

### ถ้าทำใหม่ ผมจะทำต่างตรงไหน

- **เขียน state machine ของ "งาน" ให้ชัดก่อนเขียน UI** — สถานะและกฎการเปลี่ยนสถานะควรเป็น
  ของโดเมน ไม่ใช่ของ UI แล้วทั้งหน้าจอและ API ใช้ร่วมกัน
- **ทำ audit log เป็นข้อบังคับตั้งแต่แรก** ไม่ใช่ของแถมที่มาเพิ่มทีหลัง
- **แยก "ข้อมูลสมมติ" กับ "ข้อมูลจริง" ให้ชัดตั้งแต่ต้น** ให้มีไฟล์ seed config ไฟล์เดียวที่เป็น
  แหล่งความจริงของข้อมูลตัวอย่าง ทุกทางเข้าอ่านจากที่เดียวกัน
- **ชุดทดสอบ integration ต้องรันกับเซิร์ฟเวอร์จริง** ชุดที่ต้องมีแอปรันอยู่ ควรแยก
  สั่งรันให้ชัดเจนว่าต้องเปิดอะไรบ้าง ไม่งั้นจะกลายเป็นเขียวตอนไม่มีเซิร์ฟเวอร์

### ตัวอย่างนี้ต่างจากของจริงตรงไหน — พูดตรง ๆ

| | ระบบจริง | ตัวอย่างนี้ |
|---|---|---|
| ฝั่งหลัง | Next.js + PostgreSQL, session cookie, RBAC 3 ระดับ, audit log ฝั่งเซิร์ฟเวอร์ | JavaScript ฝั่งเบราว์เซอร์ เก็บข้อมูลใน memory |
| การยืนยันตัวตน | บัญชีผู้ใช้ + การจำกัดอัตราการลองรหัสผ่าน | ไม่มี (ตั้งใจ — เพราะเป้าหมายคือสาธารณะ) |
| ขนาดจริง | หลายสิบสาขา หลายหน่วยงาน ประวัติหลายปี | 7 งานตัวอย่าง |
| ส่วนที่ยังไม่มี | — | สร้าง QR/PDF, ส่งเมลจริง, Excel export, โหลดงานจริง |

ผมทำตัวอย่างนี้ขึ้นมาเพราะโค้ดจริงเปิดเผยไม่ได้ แต่ **แนวคิดและบทเรียนเปิดเผยได้** —
ซึ่งเป็นส่วนที่ผู้จ้างส่วนใหญ่อยากเห็นอยู่แล้ว

## ที่มาและขอบเขต

ระบบจริงที่เล่าไปข้างบนเป็นงานที่ผมพัฒนาระหว่างที่งาน **ซอร์สโค้ดและข้อมูลขององค์กรนั้น
เป็นทรัพย์สินขององค์กร และยังไม่ได้เปิดเผย** — ผมจึงไม่ได้นำโค้ดจริงมาเผยแพร่ที่นี่
ทั้งที่โค้ดตัวอย่างนี้เป็นงานที่ผมเขียนขึ้นใหม่ทั้งหมด ไม่ได้ยกโค้ดจากระบบจริงมาแตกแต่ง

ในตัวอย่างนี้มีแต่ข้อมูลสมมติ: ชื่อสาขา ชื่อช่าง ชื่อพนักงาน และรายละเอียดงานทั้งหมด
ถูกสร้างขึ้นเพื่อการสาธิต ระบบจริงไม่มีชื่อบริษัท โฮสต์เนม ที่อยู่เครื่อง หรือเอกสารภายใน
ใด ๆ ปรากฏในไฟล์นี้

ถ้าคุณอยากคุยเรื่องสถาปัตยกรรมจริง เรื่อง trade-off ที่เจอ หรืออยากดูโค้ดส่วนที่
เผยแพร่ได้ ยินดีคุยโดยตรง — ติดต่อได้ทาง GitHub profile ของ BornCode
